## 2026-05-07

### 本次变更概述

本次主要把 Breakpad 崩溃转储能力从 MtAssistant 应用层迁移到 `nsdk` 库中，由 `nsdk` 统一负责初始化、目录创建、dump 回调和依赖链接配置。调用方只需要链接新版 `libnsdk` 并调用 `nsdk::InitBreakpad()`，不再直接依赖 Breakpad 的三个静态库。

### 新增崩溃转储接口

- 更新 [nsdk.h](F:\开发资料\MyCode\kds-notes\c++\nsdk\include\nsdk.h)：
  - 新增导出接口 `NSDK_API int InitBreakpad(const char* p_szDumpPath = nullptr);`。
  - `p_szDumpPath` 允许调用方传入 dump 保存目录。
  - `p_szDumpPath` 为空或未传入时，默认使用 `GetRootPath() + CrashDumps`。
  - 接口返回 `NSDK_OK` 表示初始化成功或已经初始化，返回 `NSDK_KO` 表示目录创建、路径转换或平台配置不满足要求。

- 更新 [nsdk.cpp](F:\开发资料\MyCode\kds-notes\c++\nsdk\src\nsdk.cpp)：

  - 新增进程生命周期级别的 `google_breakpad::ExceptionHandler* g_pBreakpad`，重复调用 `InitBreakpad()` 时直接返回成功，不重复创建 handler。
  - 初始化时先调用 `RegularPath()` 规范路径，再使用 `FolderExists()` 判断目录是否存在，目录不存在时调用 `CreateFolder()` 创建。

  - 非 Windows 或未开启 `NSDK_ENABLE_BREAKPAD` 时，`InitBreakpad()` 明确返回 `NSDK_KO`。

### 二次复核问题说明

- 命名锁 `CMutex` 的原问题：
  - 初版实现主要依赖共享内存中的 `m_iRefCount` 判断命名锁是否仍然有效。
  - 这种做法在“进程异常退出、未执行 `Close()`”时并不可靠，因为计数不会被系统自动回收，下一次同名 `Create()` 可能直接复用旧共享对象。
  - 对锁而言，结果是共享内存和锁文件可能长期残留；对上层而言，更大的问题是调用方会误以为拿到的是“全新命名锁”，实际上拿到的是上一次运行残留的同步对象。
  - 因此本次改为通过协调锁判断是否仍有活跃持有者：如果没有活跃持有者，则优先重建命名锁对象，确保异常退出后不会继续复用陈旧状态。

- 命名事件 `CEvent` 的原问题：
  - 初版实现同样依赖共享内存中的引用计数判断对象生命周期。
  - 这在异常退出后会带来比锁更明显的行为污染：旧的 `m_bSignaled` 和 `m_bManualReset` 状态可能被下一轮运行直接继承，形成“幽灵信号”或错误复位模式。
  - 因此本次与命名锁保持同一处理策略：没有活跃持有者时重建共享事件对象，保证事件状态不会跨异常退出被错误继承。

- 线程 `CBaseThread` 的原问题：
  - 初版 `Pause()` 在复位 `m_clEventWork` 后立即返回，且会提前把 `idle` 事件置位；如果此时线程仍在执行本轮 `Work()`，调用方会误判线程已经停下。
  - 初版 `DeleteThread()` 和 `Pause()` 没有防御线程自身调用自己的场景；一旦在工作线程内部调用，就可能出现等待自己退出或等待自己进入 idle 的死锁。
  - 因此本次把 `Pause()` 改为等待线程真正进入 idle 后再返回，并为 `Pause()` / `DeleteThread()` 增加线程自身调用防护。

### 修改原因与残余风险

- 为什么要这样修改：
  - 这次修改的目标不是单纯“让代码能跑”，而是保证命名同步对象在异常退出后的行为可预测，避免把上一轮进程的脏状态带到下一轮运行。
  - 对线程模型来说，重点是让 `Pause()` / `IsRunning()` / `DeleteThread()` 的语义与实际执行状态一致，减少调用方基于错误状态做资源释放或状态切换的风险。

- 这样修改后仍需注意的隐患：
  - 命名锁和命名事件现在不再保留“没有活跃持有者后的历史状态”。如果未来业务期望“同名事件在所有进程退出后仍保留之前的 signaled 状态”，当前实现不会满足，这属于有意选择的语义取舍。
  - `Pause()` 和外部线程调用的 `DeleteThread()` 现在会等待线程真正进入可暂停/可退出状态；如果派生类 `Work()` 内部存在长时间阻塞、死循环或不可中断等待，这两个接口仍可能等待较长时间，甚至一直阻塞。这是当前线程模型的剩余约束，不是本次修复新引入的问题。
  - 线程自身调用 `DeleteThread()` 现在会返回失败并仅发出退出请求，资源最终回收必须由外部拥有者完成；这是为了避免自等待死锁而引入的显式约束。

## 2026-07-02 Token 生成/校验底层优化

### 本次变更概述

本次针对 TradingTerminal 使用 `nsdk` 生成和校验 token 的耗时问题，新增服务端明文客户信息直连生成与快速校验接口；保持原有 token 明文格式、AES/Base64 算法、错误码语义和旧接口兼容，不引入上层 token 缓存。

### 新增接口

- 新增 `BuildFeatrueByPlainClientInfo(const std::string& clientInfo, int authDay, std::string& feature)`：
  - 适用于服务端已经拿到明文客户信息的场景。
  - 直接构造 `clientInfo + authKey + signature + startDate + endDate` 后执行一次 AES 加密。
  - 替代旧的 `MakeFeatrue + BuildFeatrue` 组合，减少一次 AES 加密和一次 AES 解密。
  - 旧 `MakeFeatrue` 和 `BuildFeatrue` 保留，避免影响其他项目调用。

- 新增 `AuthFeatrueByPlainClientInfo(const std::string& clientInfo, const std::string& feature, std::string& featureInfo)`：
  - 返回码与 `AuthFeatrue` 保持一致。
  - 保持一次 AES 解密校验流程。
  - 使用固定偏移和 `compare(pos, len, value)` 校验客户信息、公钥和签名，减少 `substr` 临时字符串。
  - 新增内部工具 `ParseAuthDate8()`，按 8 位日期字段解析开始日期和结束日期。

### 调用方影响

- TradingTerminal 的 `BuildVerifyPasswordToken()` 已改为调用 `BuildFeatrueByPlainClientInfo()`。
- TradingTerminal 的 `CheckToken()` 已改为调用 `AuthFeatrueByPlainClientInfo()`。
- MT4/MT5 `/verify_password` 继续使用 `auth_day=0`，与 `nsdk` 当前 `AUTH_DAY=0` 校验规则保持一致。
- 新增 token 生成耗时日志和 token 校验慢日志；日志不输出 token 明文。

### 性能验证

- 使用临时 benchmark 进行 10 万次循环对比，测试账号为 `7800005`，`authDay=0`。
- 旧生成链路 `MakeFeatrue + BuildFeatrue`：约 `3.656us/次`。
- 新生成链路 `BuildFeatrueByPlainClientInfo`：约 `1.064us/次`。
- token 生成速度约提升 `3.44 倍`。
- 旧校验链路 `AuthFeatrue`：约 `1.718us/次`。
- 新校验链路 `AuthFeatrueByPlainClientInfo`：约 `1.674us/次`。
- token 校验速度约提升 `1.03 倍`，说明校验侧主要耗时仍在 AES/Base64 解密本身。

- `nsdk` 使用 VS2022 `Release|x64` 编译通过，结果为 `0 error`。
- 已生成并同步 `libnsdk.dll`、`libnsdk.lib`、`libnsdk.pdb` 到 TradingTerminal 的 `vender\nsdk\lib\x64vc14` 和运行目录。

### 兼容性说明

- 本次不修改 AES 算法、Base64 格式、token 字段格式、header 名称、业务错误码和客户端协议。
- 已发出的旧 token 仍按现有 `AuthFeatrue`/新快速校验规则判断；结束日期不是当天的 token 在当前 `AUTH_DAY=0` 规则下仍会失败。
