# TradingTerminal V3 服务启动操作手册

## 1. 文档目的

本文档说明 TradingTerminal V3 在 Windows 11 环境中的完整启动、注册、检查、重启和停止流程。当前部署由以下组件组成：

1. IceGrid Registry：注册中心和 Locator，六个服务运行时必须能够连接它。
2. IceGrid Node：注册到 Registry 的业务进程宿主，根据应用描述常驻托管六个服务，并在服务异常退出后重新拉起。
3. IceGrid Admin：用于查看 Node、Application 和 Adapter 注册状态。
4. NATS JetStream：为 `MtEventService` 提供交易和配置事件的持久化、幂等追加、重投和消费者进度管理。
5. TradingTerminal 六服务：`MtEventService`、`MtQueryService`、`MtQuoteService`、`MtTradeService`、`MtDeriveService`、`MtGatewayService`。
6. Nginx：两台业务机上的 HTTPS/WSS 入口，HTTP 使用 `least_conn`，WebSocket 使用一致性粘性。
7. WinSW：只托管 NATS 和 Nginx；六个业务 EXE 始终由 IceGrid Node 独占托管。

本文档中的操作全部在 `cmd.exe` 或 `.bat` 中执行，不使用 PowerShell。

| 组件 | 端口 | 用途 |
| --- | ---: | --- |

| MtGatewayServiceRPC | 30001 | MtGatewayService 内部 Binary RPC/PUT |
| MtQuoteServiceRPC | 30002 | 行情服务内部 Binary RPC/PUT |
| MtTradeServiceRPC | 30003 | 交易服务内部 Binary RPC/PUT |
| MtQueryServiceRPC | 30004 | 查询服务内部 Binary RPC/PUT |
| MtEventServiceRPC | 30005 | 事件中心内部 Binary RPC/PUT 和推送注册 |
| MtDeriveServiceRPC | 30006 | 派生服务内部 Binary RPC/PUT |
| MtGatewayService HTTP | 28080 | 28 个正式 HTTP URL 和健康检查入口 |

| NATS Client | 4222 | MtEventService 连接 NATS 和 JetStream 的客户端入口 |

启动前可以用以下命令检查监听端口：

```bat
netstat -ano | findstr "LISTENING"
```

如果上述端口已被其他程序占用，应先定位 PID 并处理冲突，不能只修改某一份 XML 而不修改调用方配置。

## 4. 构建和运行包检查

首次部署或源码修改后，在 cmd 中执行：

```bat
cd /d F:\gwz\trank\mt5-terminal-v3
build.bat 2 test
verify_runtime.bat
```

`conf` 只维护六服务各自的 `dev/test` 模板，共 12 份 XML；不维护无后缀源配置。`build.bat` 顶部的 `PACKAGE_DIR` 是 Tags 目标路径，`PACKAGE_MODE=1` 表示全量打包，`PACKAGE_MODE=2` 表示增量打包，第二个参数只允许 `dev/test`：

```bat
build.bat 1 test
build.bat 2 dev
```

两种模式都会先 Clean、再 Build，然后将选中环境模板重命名为六份无后缀 XML，并打包六个 EXE/PDB、六份运行 XML、所需基础网络/PostgreSQL/NATS 客户端运行库、`mtmanapi64.dll` 和三个原生 x64 MT5 Manager DLL：`MT5APIManager64.dll`、`MT5APIManager64avx.dll`、`MT5APIManager64avx2.dll`。增量模式跳过内容相同的 XML/DLL，全量模式强制覆盖 DLL；Tags 不携带 `_dev.xml`、`_test.xml`。构建会清理误入运行目录的 ARM64 和 .NET 包装 DLL，流程结束后只删除工程根目录的 `Temp`。

`verify_runtime.bat` 同时检查六个同名 PDB 和三个 MT5 x64 Manager DLL；任一文件缺失都视为运行包不完整。厂商完整 SDK 仍保存在 `vender\mt5sdk`，不得从该归档目录删除 ARM64 或 .NET 文件。

只部署配置而不重新构建时执行：

```bat
deploy_config.bat dev
deploy_config.bat test
deploy_config.bat test D:\TradingTerminal
deploy_config.bat test D:\TradingTerminal-Node1 CloudNetNode1 1
deploy_config.bat test D:\TradingTerminal-Node2 CloudNetNode2 2
```

前两个命令默认部署到 `bin\x64vc14`，第三个命令部署到指定目录。第四、第五个命令用于两业务 Node，脚本还会生成唯一 `instanceId/pluginId/AdapterId`、独立数据目录和同 Node Event 代理。脚本会校验六份模板完整后，再覆盖生成目标目录中的六份 `<Service>.xml`。

期望结果：

```text

0 个警告
0 个错误
VERIFY_OK: executables, configurations and runtime DLLs are complete.
```



## 5. 启动 NATS JetStream

### 5.1 根据环境决定是否启动

V3 只维护 `dev/test` 两类配置模板。执行 `deploy_config.bat dev` 或 `deploy_config.bat test` 后，所选模板会被复制并重命名为 EXE 同目录的 `MtEventService.xml`，程序不会直接读取带环境后缀的模板。

- `dev`：Event 的 `<Cluster enable="0">`、`<Broadcast enable="0">`，但 `<ReliableEvent enable="1" replicas="1">`；启动 Event 前必须先启动单节点 JetStream。
- `test`：与 dev 一样关闭 Event Cluster/Broadcast、启用单副本 ReliableEvent；差异只来自测试行情源、凭据和其他业务配置，不得启用第二个 Event 实例。
- Quote 的 dev/test 均缺少生效 Cluster，只运行单实例、每个 `Version+No` 一条 `QUOTE_PUMPING` 连接；`1211` 不进入 NATS。

### 5.2 第一阶段单节点启动

第一阶段目标是 V3 六服务完整平替 V2 单体服务的业务功能，暂不验收 NATS 基础设施高可用。单节点 JetStream 只承载 Event `1172-1175` 可靠事件；Quote `1211`、Derive `1251/1252` 均由单 Event 实例通过 Ice 在线中继，不使用 KV 租约、Core NATS Broadcast 或 Tick Stream。

在独立 cmd 窗口执行：

```bat
E:\nats\nats-server.exe --version
if not exist E:\nats\data mkdir E:\nats\data
E:\nats\nats-server.exe -js -sd E:\nats\data -a 127.0.0.1 -p 4222 -m 8222
```

关键参数说明：

- `-js`：启用 JetStream，不能省略。缺少该参数时只是普通 NATS Server，MtEventService 无法创建或访问 Stream。
- `-sd E:\nats\data`：指定 JetStream 持久化目录。目录必须位于稳定磁盘，运行账户需要读写权限，并应监控可用空间。
- `-a 127.0.0.1`：只接受本机连接。NATS Server 未指定 `-a` 时默认绑定 `0.0.0.0`；本文显式限制为本机地址。NATS 部署在远程机器时改为该机器的业务网 IP，并同步配置防火墙和 MtEventService URL。
- `-p 4222`：NATS 客户端端口，与当前 `MtEventService_test.xml` 的默认 URL 一致。
- `-m 8222`：启用 HTTP 监控，仅用于测试和受控运维网络，不应暴露到公网。

保持该窗口运行，并在另一个 cmd 窗口验证：

```bat
netstat -ano | findstr ":4222"
netstat -ano | findstr ":8222"
curl http://127.0.0.1:8222/jsz
```

`4222` 和 `8222` 应显示 `LISTENING`，`/jsz` 应返回 JetStream JSON 状态。只看到 `4222` 监听不能证明 JetStream 已启用，必须同时检查启动参数、NATS 输出或 `/jsz`。

项目内置配置的推荐启动和检查方式：

```bat
cd /d F:\gwz\trank\mt5-terminal-v3\tools\NATS
tool\verify_binary.bat
tool\start_cluster.bat
tool\check_cluster.bat
```

虽然脚本名为 `start_cluster.bat`，第一阶段只启动 Node1，并只检查客户端 `4222` 和监控 `8222`。原 Node2/Node3 启动命令、`cluster/routes`、`4322/4422/6222/6322/6422` 和 `8322/8422` 检查均以“第二阶段高可用”注释或预留文件保留，不得在第一阶段局部取消注释。

### 5.3 Event Reliable 配置和认证

第一阶段只在 `MtEventService.xml` 的 `<ReliableEvent>` 中配置 Node1 地址和受控凭据。Event Cluster、Event Broadcast、Quote Cluster 和 Quote Tick Stream 均不生效；第二阶段示例必须继续保留在 XML 注释中。

模板中的真实值不得复制到文档、日志、错误或 `1103` 响应。以下只展示结构：

```xml
<Cluster enable="0" />
<MtEventService>
	<MarketEvent workerThreads="4" queueCapacity="0" dropLogIntervalMs="10000" />
	<Broadcast enable="0" subject="mt.event.broadcast" />
	<ReliableEvent enable="1" url="nats://replace-user:replace-password@node1:4222"
		stream="MT_TRADING_EVENTS" subjectPrefix="mt.trade" replicas="1" />
</MtEventService>
```

`deploy_config.bat` 会把选中的模板复制为运行目录同名 XML，再按 Node 和实例编号改写 `instanceId`、`adapterId`、pluginId、数据目录和同 Node Event 代理。部署后必须限制 XML 只对服务账户和授权运维人员可读。

当前客户端支持 NATS URL、用户名和密码，不提供独立 NKey、JWT、credentials 文件或 TLS 客户端配置。需要更高级认证时必须先新增客户端能力和测试，不能只修改服务端配置。

### 5.4 V3 中的 JetStream 数据链路

MtEventService 启动 Reliable 引擎时会创建或校验名为 `MT_TRADING_EVENTS` 的文件存储 Stream，Subject 范围为 `mt.trade.>`。运维不需要手工预建同名 Stream，但已有 Stream 的范围和保留参数必须与 XML 兼容。

- `1172`：MtTradeService 从 durable file outbox 提交事件；MtEventService 使用 `Nats-Msg-Id=EventId` 实现幂等追加。
- `1173`：MtDeriveService 通过 durable pull consumer 批量拉取事件。
- `1174`：消费者完成本地处理后显式 ACK；未 ACK 消息在 AckWait 到期或消费者重启后重新投递。
- `1175`：查询 Stream、Consumer、积压和容量状态。

交易已经成功但 MtEventService 或 NATS 暂时不可用时，不能重新提交原交易请求。事件应保留在 MtTradeService outbox，依赖恢复后自动补交；运维通过 Trade 日志、Event 日志、`1175` 和 NATS `/jsz` 共同确认积压下降。

第一阶段不创建或依赖 `MT_TRADING_CLUSTER` KV、`MT_DERIVE_TICKS` Tick Stream 或 Event Broadcast Subject。这些资源仅属于第二阶段多实例接管方案，不能通过局部取消 XML 注释提前启用。

Trade 幂等和 outbox 当前仍位于本机数据目录，只保证同机进程重启恢复。整台业务机或磁盘丢失时，不能仅依靠 NATS KV 恢复尚未投递的本地事件；第二阶段 PostgreSQL transactional outbox 完成前，必须保留权威 MT 对账和人工回滚流程。

正式环境必须将 NATS Server 注册为受监控的后台服务，并对 `E:\nats\data` 对应的现场目录设置磁盘告警、权限和备份策略。停止或升级 NATS 时不得删除、清空或临时替换 JetStream 数据目录。

## 6. 安装或启动 IceGrid Registry

### 6.1 单机 dev/诊断模式

首次部署时，以管理员身份打开 cmd，执行总安装脚本：

```bat
cd /d F:\gwz\trank\mt5-terminal-v3\tools\IceGrid
tool\install_icegrid_wtgrid.bat
```

该脚本安装并启动 `icegridregistry.MtIceGrid` 和 `icegridnode.MtIceGrid.CloudNetNode1` 两个自动启动的 Windows 服务。成功后关闭安装窗口不影响服务后台运行。

`tools\IceGrid\tool` 下全部 8 个批处理必须保持 ASCII 可执行文本与 CRLF。正式执行前可以先运行对应脚本的 `--help`；帮助完整显示且没有 `is not recognized as an internal or external command` 才继续。帮助模式位于权限检查和副作用之前，不会安装或启动服务、连接 Registry 或启动前台进程。

服务已经安装但 Registry 处于停止状态时，执行：

```bat
tool\start_registry.bat
```

Registry 使用以下关键配置：

```ini
IceGrid.InstanceName=MtIceGrid
IceGrid.Registry.Client.Endpoints=default -h 127.0.0.1 -p 18000 -t 10000
IceGrid.Registry.DynamicRegistration=1
Ice.ProgramName=MtIceGridRegistry
```

其中 `DynamicRegistration=1` 保留给前台诊断和特殊部署场景；正式部署的六服务由 IceGrid 应用描述注册 Adapter 和副本组。

启动后检查 18000 端口：

```bat
netstat -ano | findstr ":18000"
```

出现 `LISTENING` 表示 Registry 已监听。若启动失败，查看：

```text
F:\gwz\trank\mt5-terminal-v3\tools\IceGrid\log\registry_stdout.txt
F:\gwz\trank\mt5-terminal-v3\tools\IceGrid\log\registry_stderr.txt
```

### 6.2 Master/Replica HA 模式

`config\registry.cfg`、`node.cfg` 和 `admin.cfg` 只用于单机 dev 和故障诊断，Locator 只包含 `18000`。test/HA 必须使用 `registry-master.cfg`、`registry-replica.cfg`、`node1-ha.cfg`、`node2-ha.cfg` 和 `admin-ha.cfg`，并把其中的 `127.0.0.1` 替换为两台 Registry 的业务网地址；六服务 XML、HA Node 和 HA Admin 的 Locator 必须同时包含 `18000` 与 `18010` 两个入口。

同机描述验证可在未安装同名 Windows 服务时执行：

```bat
cd /d F:\gwz\trank\mt5-terminal-v3\tools\IceGrid
tool\start_ha_registry.bat
netstat -ano | findstr ":18000"
netstat -ano | findstr ":18010"
```

该脚本会拒绝正在运行的默认 Registry Windows 服务以及 18000/18010 端口冲突，启动 Master 后先验证 Admin 端点，再启动 Replica 并等待 18010 监听。它只用于同机前台诊断，不替代生产 Windows 服务；任一步失败时查看两个 Registry stderr，禁止重复执行制造多个进程。

生产环境 Master 和 Replica 必须分别作为自动启动的 Registry 服务运行，使用独立 LMDB 和日志目录。详细安装、故障切换和权限配置以 `tools\IceGrid\部署步骤.md` 的 HA 章节为准；Master 故障时暂停应用部署和管理写操作，既有 Locator 发现通过 Replica 继续。

## 7. 启动 IceGrid Node

### 7.1 单机 dev/诊断模式

Registry 服务健康后，启动已经安装的 Node 服务：

启动前确认 `tools\IceGrid\config\node.cfg` 至少包含以下配置：

```ini
Ice.Default.Locator=MtIceGrid/Locator:default -h 127.0.0.1 -p 18000
IceGrid.Node.Name=CloudNetNode1
IceGrid.Node.Endpoints=default -h 127.0.0.1
```

`IceGrid.Node.Endpoints` 是 Ice 3.8.2 Node 的必填管理端点。缺少该项时，`icegridnode.exe` 会在初始化阶段退出或无法注册，表现为 `start_node.bat` 一直等待；不指定端口时由系统分配并登记到 Registry。远程部署时将 `-h 127.0.0.1` 改为 Node 所在机器可被 Registry 访问的业务网 IP，并同步检查防火墙。

```bat
cd /d F:\gwz\trank\mt5-terminal-v3\tools\IceGrid
tool\start_node.bat
```

Node 名称固定为 `CloudNetNode1`，数据目录为 `db\node1`。脚本确认 Node 注册成功后立即退出，Node 继续由 Windows 服务在后台运行。

当前阶段必须明确：

- Node 已接入 Registry，并负责常驻托管六个服务。
- dev 应用描述为 `app\MtApplication_dev.xml`，只包含 `CloudNetNode1` 和六个 `*-1` Server；执行 `tool\deploy_app.bat dev` 前必须先把六个 `server-instance.exe` 改为 Node 能访问的真实路径。
- 六个 Server 使用 `activation="always"` 和 `activation-timeout="30"`。Node 启动或应用部署后会自动拉起服务，服务异常退出后由 Node 重新激活。
- `start_all.bat` 和逐个运行 EXE 只用于前台诊断。诊断前必须先在 IceGrid Admin 中停止对应托管 Server，禁止两个实例同时绑定同一端口或写同一数据目录。

Node 日志位于：

```text
F:\gwz\trank\mt5-terminal-v3\tools\IceGrid\log\node_stdout.txt
F:\gwz\trank\mt5-terminal-v3\tools\IceGrid\log\node_stderr.txt
```

### 7.2 两业务 Node 模式

两台业务机分别使用 `node1-ha.cfg` 和 `node2-ha.cfg`，名称固定为 `CloudNetNode1/CloudNetNode2`，数据目录和日志目录必须独立。配置中的 Locator 同时列出 Master/Replica，`IceGrid.Node.Endpoints` 必须发布对 Registry 可达的业务网地址。

同机描述验证可在没有已安装同名 Node 服务时执行：

```bat
cd /d F:\gwz\trank\mt5-terminal-v3\tools\IceGrid
tool\start_ha_nodes.bat
```

## 9. 标准启动顺序和六服务依赖

### 9.1 标准启动步骤

测试环境推荐严格按以下顺序操作：

1. 构建一次，然后分别执行 `deploy_config.bat test <Node1运行目录> CloudNetNode1 1` 和 `deploy_config.bat test <Node2运行目录> CloudNetNode2 2`，生成两套唯一实例 XML。
2. 启动第一阶段单节点 NATS JetStream，确认 KV/Stream 副本数为 1，再启动 PostgreSQL 和 MT4/MT5 测试节点；三节点和副本数 3 留到第二阶段。
3. 启动 IceGrid Master/Replica Registry，确认 18000/18010 和双 Locator 可用。
4. 启动两个业务 Node，Admin 的 `node list` 必须同时看到 `CloudNetNode1/CloudNetNode2`。
5. 核对 `tools\IceGrid\app\MtApplication_test.xml` 中两个 Node 的 EXE 路径，执行 `tool\deploy_app.bat test`。
6. Node 根据 `activation="always"` 自动启动 12 个服务实例；不得执行 `start_all.bat` 或逐个双击 EXE。
7. 使用 Admin 检查 Application、12 个 Server/Adapter 和六个 Replica Group；使用 `1103` 检查实例、Owner、租约代次和恢复状态。
8. 启动两台 Nginx，再启用外部 L4 VIP；检查 Reliable/Event 广播、`MT_DERIVE_TICKS`、Trade outbox 和 Gateway Owner 路由，最后验证 HTTP、WebSocket 和 V2/V3 差分接口。

### 9.2 六服务就绪关系

推荐顺序如下：

| 顺序 | 服务 | 依赖 | 启动成功后的作用 |
| ---: | --- | --- | --- |
| 1 | MtEventService | Registry；Quote 可晚启动；启用 Reliable 时依赖 NATS JetStream | 启动 `1211` 中继和可选 `1172-1175` 可靠事件中心 |
| 2 | MtQueryService | Registry、MtQuoteService 时间权威；Event 可晚启动；PostgreSQL 可降级 | 发布 READY 前调用 `1123` 完成时间引导，再订阅增量并安装业务快照 |
| 3 | MtQuoteService | Registry、MT Manager SDK 和凭据 | 接入 MT4/MT5 行情并发布 `1211`，不主动连接 Event |
| 4 | MtTradeService | Registry、MtEventService、NATS KV、MT Manager SDK 和 XML 节点凭据 | 提供 `1132-1142`、Owner 对账、持久化幂等和 durable outbox |
| 5 | MtDeriveService | Registry、MtEventService、MtQueryService | 订阅事件并访问查询服务 |
| 6 | MtGatewayService | Registry、其余五服务 | 启动 HTTP/WebSocket、路由和健康监控 |

IceGrid 可以同时激活六个 Server，CloudNetDataApi 会按表中依赖持续重连，因此不要求人工按顺序逐个启动。表中的顺序用于理解就绪过程、故障排查和受控升级；MtGatewayService 只有在依赖服务进入 `READY` 后才会把对应流量转发过去。

### 10.2 MtQueryService

```bat

MtQueryService.exe
```

成功标志：控制台出现 `MtQueryService startup succeeded.` 和版本，主日志出现 `service startup completed`，Adapter 为 `MtQueryServiceRPC`，端口为 30004。

默认 `PostgreSQL enable="0"`，此时 `1165/1166` 返回 `POSTGRES_POOL_DISABLED`，不影响 `1101`、`1156` 和 `1157`。启用 ClientData 前，先由数据库管理员执行幂等脚本：

```bat
psql -h your-pg-host -p 5432 -U your-pg-user -d your-pg-database -f F:\gwz\trank\mt5-terminal-v3\docs\sql\MtQueryServiceClientData.sql
```

随后在受控模板的 `<PostgreSQL enable="1">` 中直接配置 host、port、database、user 和明文 password，再执行 `deploy_config.bat`。真实值不得进入文档、日志或状态接口；部署后的 XML 必须限制文件权限。

服务只执行只读表结构检查，不会自动创建或修改数据库对象。数据库断开、配置缺失或缺表时进程保持运行，`1152` 的 `PostgreSQL.State/Detail` 给出具体降级原因。

Query 在发布进程 `READY` 前先调用 MtQuoteService `1123` 引导全部启用 `Version+No` 的时间权威。`timeBootstrapTimeoutMs` 合法范围为 `1000-300000` 毫秒且启动后不可热更新：dev 配置为 `5000` 并允许降级，超时后缺失节点的 `/bars` 返回 `20008`，后续 `1123/1244` 恢复后无需重启；test 配置为 `60000` 且禁止降级，超时会启动失败，Gateway 不得选中该实例。时间引导完成后，Query 才启动 `1122/1185` 业务快照线程；业务快照未完成时 `1156/1157` 仍返回对应来源未就绪错误。

### 10.3 MtQuoteService

MtQuoteService 从部署后的 XML `<Connections>` 读取每个 `Version+No` 的 `QUOTE_PUMPING` 地址、账号和明文密码，不读取凭据环境变量。先用 `deploy_config.bat` 生成当前 Node 的同名 XML，再启动：

```bat
cd /d F:\gwz\trank\mt5-terminal-v3\bin\x64vc14
MtQuoteService.exe
```

进程启动成功标志：控制台出现 `MtQuoteService startup succeeded.` 和版本，主日志出现 `service startup completed`，Adapter 为 `MtQuoteServiceRPC`，端口为 30002。

每个启用节点的最后有效服务器时间偏移与 V2 使用同一目录、文件名和 JSON 字段：

```text
bin\x64vc14\data\mt4\<No>\server_time_offset.json
bin\x64vc14\data\mt5\<No>\server_time_offset.json
```

文件固定包含 `Version=1`、`Platform`、`No`、`OffsetSeconds`、`Source` 和 `UpdatedAtMs`。当前 Owner 启动或接管后先校验并加载对应文件，再连接 MT 在线校时；在线值成功后按临时文件、磁盘刷新和原子替换写回。连接失败、断线、重连或周期采样失败不会清除最后有效偏移，而是按同步周期续期同一个 Epoch/Generation；在线值恢复后自动覆盖本地值。Standby 不加载、不续期也不发布其他节点的缓存。

`/server_info` 保持 V2 整批语义：全部选中节点都有在线值或本地值时返回 `Code=0`；任一节点两种值都不存在时整批返回 `20008`，不得以 `0` 偏移、本机时区或部分成功掩盖故障。文件缺失、JSON 损坏、`Version/Platform/No` 不匹配或偏移超出 `-86400..86400` 时只记录警告并继续尝试在线校时。旧 V3 的 `cache\MtQuoteService\snapshot\time-authority.bin` 已停止读写；确认所有启用节点的新 JSON 已生成后可以人工清理，升级脚本和服务不会自动删除。

行情真正就绪还必须检查：

- MT5 日志出现 `MT5 quote stream ready`；MT4 日志出现 `MT4 quote connection registered` 和 `MT4 quote symbols subscribed`。
- MtEventService 已连接 `MtQuoteServiceRPC` 并完成 `pluginId=MtEventService-Quote-01`、`subInfo=|1211` 的注册。
- `bin\x64vc14` 同时存在 `mtmanapi64.dll`、`MT5APIManager64.dll`、`MT5APIManager64avx.dll`、`MT5APIManager64avx2.dll`；不得包含 ARM64 或 `MetaQuotes.MT5*API64.dll` .NET 包装库。

`1211` 是 Best Effort 行情。MtEventService 尚未完成注册时产生的 Tick 不会补发，因此启动 Quote 后应等待 Event 注册恢复，再开始 Web 行情验收。

### 10.7 启动后内存与积压检查

启动后先预热 30 分钟，再通过内部 `1103 v2` 连续采集 Private Bytes、Working Set、线程、句柄、日志队列和通知拒绝计数。任务管理器工作集只能辅助观察，不能单独作为泄漏结论。

- Quote：逐 `Version+No` 检查 WAL 字节、ACK 段号/偏移、当前批次和最老积压。Derive 不可用时 WAL 允许增长，但当前内存批次不得超过 `batchTicks`；恢复后 ACK 必须前进并释放已确认段。
- Trade：检查五类角色实际连接数、重连次数、Dealer 各状态和 outbox。终态按 `dealerRetentionHours` 清理，`SUBMITTED/UNKNOWN` 不得被自动删除。
- Query：检查 PostgreSQL 状态、历史保存任务/Bar/字节计数和锁分片数。锁分片固定为 256，保存队列不得超过 256 个任务、262144 根 Bar 或 64 MiB。
- 六服务：日志队列不得超过 XML 的 `maxQueueEntries/maxQueueBytes`；高频未知或拒绝通知应表现为每分钟摘要和计数增长，不应逐条产生 INFO 日志。

第一阶段正式验收要求同一发布目录完成两小时稳态斜率和 72 小时测试。预热后 Private Bytes 增长斜率目标不超过 `2 MiB/小时`；未取得报告前仍按“可联调、不可生产平替”处理。

## 15. 单个服务重启和自愈验证

以 MtDeriveService 为例：

1. 受控升级时，在 Admin 执行 `server stop MtDeriveServiceRPC-1`，确认服务完成反向资源释放。
2. MtGatewayService 的 `1103` 探测失败后清除该实例的陈旧租约并标记 `DOWN`；Owner 流量只在新实例报告 READY Owner 后恢复。
3. 更新 EXE、PDB 和同名 XML 后执行 `server start MtDeriveServiceRPC-1`。
4. MtDeriveService 重新向 Registry 注册 Adapter，以 Standby 重新竞争租约，完成状态恢复后通过 `1103` 报告 READY Owner；CloudNetDataApi 定时重连。
5. 自愈演练使用测试环境故障注入令进程异常退出，不使用 `server stop`。Node 应在 30 秒内重新激活进程，并在 `bin\x64vc14\dump\MtDeriveService` 留下 dump 和 `last_crash.txt`。

同样的方法验证其他五个服务。受控 stop 不应被当成崩溃自动重启；服务已在应用描述中声明时，不需要重启 Registry、Node 或 MtGatewayService。

## 16. 停止顺序

HA 受控停机按以下顺序执行：

1. 先从外部 L4 VIP 摘除两台 Nginx，再使用 `MtNginx.exe stop` 停止入口。
2. 在 Admin 中停止两个 MtGatewayService Server。
3. 等待在途交易完成并检查两个 MtTradeService 的节点本地 outbox；存在待投递事件时保持 Trade、Event 和 NATS 运行，等待积压归零。
4. 按分片释放 Derive、Quote、Trade 租约，确认 Standby 不再接管后停止两个 Derive、Quote、Trade 和 Query 实例。
5. 停止两个 MtEventService；停止前确认没有必须保留的在途 `1172-1175` 调用。
6. 停止 CloudNetNode2、CloudNetNode1 Windows 服务。
7. 停止 Replica Registry，再停止 Master Registry。
8. 最后依次使用对应 `MtNatsNode*.exe stop` 停止 NATS；不得删除或清空任何 JetStream `store_dir`。

前台诊断实例可以按 `Ctrl+C`、`Ctrl+Break` 或点击控制台右上角关闭。程序收到控制事件后只设置停止标记，由主线程反向停止 HTTP/Web、监控和 CloudNetDataApi，最后排空日志。任务管理器的“结束任务”在部分 Windows 场景会直接调用强制终止，进程没有机会执行析构，因此只用于进程已经无响应的兜底处理。Admin 控制台输入 `exit` 只会退出管理端，不会停止其他组件。

## 17. 常见错误处理

| 现象或错误 | 原因 | 处理方式 |
| --- | --- | --- |
| `Ice::ConnectionRefusedException` | Registry 未启动或 Locator 地址错误 | 先启动 Registry，核对六份 XML 和 `registry.cfg` 的 `MtIceGrid/Locator` 地址 |
| `Ice::NotRegisteredException` | 目标 Adapter 尚未注册或 AdapterId 不一致 | 检查目标服务是否 `service ready`，再用 `adapter list` 检查 `{Service}RPC` |
| `CONFIG_FILE_NOT_FOUND` | EXE 同目录缺少对应 XML | 重新执行 `deploy_config.bat dev` 或 `deploy_config.bat test` 后运行 `verify_runtime.bat` |
| 运行 `install_icegrid_wtgrid.bat` 时中文片段连续提示 `is not recognized as an internal or external command` | 批处理包含 UTF-8 多字节可执行文本、裸 LF 或被编辑器改成混合换行，`CALL/GOTO` 返回后发生字节偏移解析 | 使用仓库中已修复的 ASCII+CRLF 安装脚本覆盖现场副本；先运行 `--help` 验证，再以管理员身份重新执行，禁止从聊天或网页复制脚本文本覆盖 `.bat` |
| 启动窗口显示 `Startup failed` | 配置、日志、CloudNet 或派生组件初始化失败 | 按 `Stage/ReturnCode/ConfigFile/Error` 定位；交互式窗口会等待 Enter，不会立即关闭 |
| MtGatewayService 返回 503 | 目标服务仍为 `STARTING` 或已经 `DOWN` | 查看 MtGatewayService 主日志和目标服务日志，等待定时重连或重启目标服务 |
| `node list` 没有 CloudNetNode1 | Node 未启动、Locator 不一致或缺少管理端点 | 确认 `node.cfg` 包含 `IceGrid.Node.Endpoints=default -h <Node IP>`，再启动 `tools\IceGrid\tool\start_node.bat`，检查 `tools\IceGrid\log\node_stderr.txt` |
| `application list` 为空 | 应用尚未部署，或 Registry 数据目录被替换、清空 | 核对对应环境 `MtApplication_dev.xml/MtApplication_test.xml` 中的真实 EXE 路径，执行 `tool\deploy_app.bat dev|test`；常规重部署不得清空 Registry 数据 |
| Server 反复启动失败 | EXE 路径错误、同名 XML 缺失、依赖 DLL 缺失、端口冲突或外部依赖不满足启动条件 | 执行 `server list` 并查看 Node stderr、服务主日志和 `dump\<ServiceName>`；修复根因后执行 `server start <ServerId>` |
| 服务端口无法监听 | 端口被占用 | 使用 `netstat -ano` 查找 PID，确认没有重复启动相同服务 |
| 推送注册失败 | Quote/Event 连接未建立或订阅数字不匹配 | 检查 MtEventService 到 `MtQuoteServiceRPC` 的连接，以及 `subInfo="|1211"` |
| MtQuoteService 提示连接角色或凭据配置非法 | XML 的 `Version+No`、`QUOTE_PUMPING`、地址、账号或密码不完整 | 修正对应 `dev/test` 模板并重新执行 `deploy_config.bat`；不得在日志或工单中粘贴密码 |
| MtQuoteService 提示 `MT4_SDK_LOAD_FAILED` 或 `MT5_SDK_LOAD_FAILED` | Manager DLL 缺失或版本不匹配 | 重新执行 `stage_runtime.bat 1`，核对 EXE 同级 MT4/MT5 Manager DLL |
| `/server_info` 返回 `20008` 且 Quote 在线校时失败 | 对应 `Version+No` 既没有实时值，也没有可用的 `server_time_offset.json` | 检查 Quote 日志中的失败阶段、MT 返回码、RTT、缓存路径和 `cacheAvailable`；从 V2 迁移同节点 JSON 或恢复 MT 连接，禁止手工伪造 `0` |
| Quote 提示时间偏移文件损坏或节点不匹配 | JSON 字段类型错误、`Version` 不是 1、`Platform/No` 与目录节点不一致，或偏移超出范围 | 先备份文件，再由在线校时自动生成新文件；不得把其他节点的缓存直接改名使用 |
| MtQueryService 启动时提示缺少 `pqxx.dll` 或 `libpq.dll` | PostgreSQL 运行库未完整部署 | 执行 `stage_runtime.bat 1`，确认 EXE 同级存在 pqxx、libpq、OpenSSL、intl、iconv 和 winpthread 七个 DLL |
| MtEventService 启动时提示 NATS DLL 缺失 | JetStream 客户端运行库未完整部署 | 执行 `stage_runtime.bat 1`，确认 EXE 同级存在 nats、libsodium、OpenSSL 四个 NATS 运行 DLL |
| NATS 已监听 4222，但 MtEventService 提示 JetStream 不可用 | NATS 启动时遗漏 `-js` | 使用带 `-js -sd <持久化目录>` 的命令重新启动，并通过 `curl http://127.0.0.1:8222/jsz` 验证 |
| NATS 的 4222 或 8222 无法监听 | 端口已占用、绑定地址错误或运行账户无权限 | 使用 `netstat -ano | findstr ":4222"` 和 `findstr ":8222"` 定位 PID，修复冲突后重启 NATS |
| MtEventService 提示 `RELIABLE_EVENT_BACKEND_FAILED` | `enable=1` 但 NATS 不可达、认证失败、JetStream 未启用或 Stream 配置非法 | 确认 NATS 使用 `-js` 启动，再核对 URL、认证、Stream、Subject、防火墙和磁盘权限 |
| NATS 返回 authorization violation | 六服务 XML 中的 NATS 用户/密码与服务端配置不一致 | 在受控机器上逐项核对模板和 NATS 配置，重新部署 XML；不要在日志、工单或状态接口中打印真实凭据 |
| `CLUSTER_QUORUM_LOST` | 两个以上 NATS 节点不可达或 KV 无法形成多数派 | 状态型服务会 fail closed；先恢复 NATS quorum，再确认实例以 Standby 重新竞争，禁止手工强制双主 |
| `SERVICE_NOT_OWNER` 或 `STALE_FENCING_TOKEN` | 请求发给 Standby，或旧 Owner 仍携带过时代次写入 | 检查 `1103` 和 KV Owner，等待 Gateway 清理陈旧租约并重新选主；交易结果不确定时禁止重试 |
| JetStream Stream 创建或校验失败 | `store_dir` 无写权限、磁盘不足，或已有 Stream 的 Subject 和保留参数不兼容 | 检查 NATS 日志、`/jsz`、磁盘空间和 XML 参数；不得通过删除生产数据目录绕过错误 |
| MtTradeService 提示交易节点凭据缺失 | XML 已启用连接，但角色的地址、账号或密码为空 | 修正对应 `dev/test` 模板并重新部署；保持五类物理连接角色隔离 |
| Nginx 服务启动失败 | 证书、上游地址、端口、相对路径或 WinSW 工作目录错误 | 先执行 `nginx.exe -t -p <Nginx根目录> -c conf/nginx.conf`，修复后再启动 `MtNginx` 服务 |
| 交易成功但 outbox 持续积压 | MtEventService、NATS、`1172` 或认证链路不可用 | 不要重放交易请求；恢复 Event/NATS 后同时检查 Trade/Event 日志、`1175` 和 `/jsz`，确认自动补交且积压持续下降 |
| `1165/1166` 返回 `POSTGRES_SCHEMA_TABLE_MISSING` | ClientData 四张活动表未部署 | 由数据库管理员执行 `docs\sql\MtQueryServiceClientData.sql`，不要依赖服务运行时自动建表 |
| `1156/1157` 返回行情未就绪或过期 | `1122` 快照未安装、`1211` 中断或报价超过 `quoteStaleMs` | 检查 Quote、Event 和 Query 日志中的快照高水位、订阅续约及节点状态 |
| MtQueryService 启动失败并提示 `QUERY_TIME_BOOTSTRAP_FAILED` | test 环境在 `timeBootstrapTimeoutMs` 内未取得全部启用节点的 READY 时间权威 | 先检查 Quote `1123`、CloudNet 连接和每个 `Version+No` 的 Epoch/Generation/有效期；不得改用本机时区或零 offset 绕过 |
| dev 的 `/bars` 返回 `20008` | Query 已按允许降级策略启动，但对应节点时间权威缺失、过期或查询期间代次改变 | 检查 Query 的 time bootstrap 日志和 Quote/Event `1123/1244`；状态恢复后直接重试，无需重启 Query |
| Web 已订阅 Quote 但没有 `10002` | MT 行情未就绪、Event 尚未注册或订阅条件不匹配 | 依次检查 Quote stream ready、Event `|1211` 注册、Gateway Event 注册和 `Version/No/SymbolIds` |
| 中文输出乱码 | cmd 代码页或文件编码不一致 | 使用项目 `.bat` 启动 IceGrid；源码、XML 和文档保持 UTF-8 |

## 18. Derive DLQ 查看、导出和重放

MtDeriveService 的 `deadLetterPath` 保存达到处理重试上限且已经写盘后才 ACK 的可靠事件。`replayPath` 是实例独占重放收件箱，`auditPath` 是 JSON Lines 操作审计；三项都在 `MtDeriveService.xml` 的 `<ReliableConsumer>` 中配置。不得直接编辑 `dead-letter.bin` 或删除 JetStream 数据。

独立工具位于 `tools\MtDeriveDlqTool`，不加入六服务主解决方案。先构建和自测：

```bat
cd /d F:\gwz\trank\mt5-terminal-v3\tools\MtDeriveDlqTool
build.bat
bin\MtDeriveDlqTool.exe --self-test
```

自测必须输出 `ALL_TESTS_PASSED`。查看和导出要求填写操作人及原因，所有动作写入同一个审计文件：

```bat
bin\MtDeriveDlqTool.exe list ^
  --dlq F:\TradingTerminal\cache\MtDeriveService\dead-letter.bin ^
  --audit F:\TradingTerminal\cache\MtDeriveService\replay-audit.jsonl ^
  --operator operator-name --reason incident-review

bin\MtDeriveDlqTool.exe export ^
  --dlq F:\TradingTerminal\cache\MtDeriveService\dead-letter.bin ^
  --event-id event-id-from-list ^
  --out F:\TradingTerminal\review\event.bin ^
  --audit F:\TradingTerminal\cache\MtDeriveService\replay-audit.jsonl ^
  --operator operator-name --reason payload-review
```

提交重放前必须核对 EventId、原失败原因、Query 权威快照和后续同实体事件。工具将完整 Binary 信封原子写成 `.request`，MtDeriveService 自动处理并将文件改为 `.done`、`.failed` 或 `.invalid`：

```bat
bin\MtDeriveDlqTool.exe replay ^
  --dlq F:\TradingTerminal\cache\MtDeriveService\dead-letter.bin ^
  --event-id event-id-from-list ^
  --inbox F:\TradingTerminal\cache\MtDeriveService\replay ^
  --audit F:\TradingTerminal\cache\MtDeriveService\replay-audit.jsonl ^
  --operator operator-name --reason approved-replay
```

- 重放不再次调用 Event `1172`，避免相同 `Nats-Msg-Id` 在 JetStream 去重窗口内被静默抑制。
- 服务复用正式 Reliable Binary 校验。来源尚未完成 `1167` 快照时保留 `.request` 等待，不提前拒绝。
- 默认按快照水位和实体 `SourceSequence` 拒绝旧事件覆盖新状态；命中实体幂等时结果为 `DUPLICATE`。
- `--allow-stale` 会显式越过顺序保护，只能在负责人批准并完成权威数据备份后使用；标志和最终结果都会写入审计。
- `SUBMITTED` 只表示请求文件已发布，不表示业务状态已应用。必须等待审计出现 `APPLIED/DUPLICATE/REJECTED`，再核对 `1184/1186` 和权威 Query 数据。
- 多实例部署必须把请求提交给当前 Owner 的实例独占 `replayPath`；不得向两个实例重复提交同一请求。
- 审计和导出文件不得包含密码、Token 或完整账户数据，事件 Binary 只能放在受控故障目录。

## 19. 最终检查清单

启动完成后逐项确认：

1. `tools\NATS\tool\verify_binary.bat` 验证 NATS `v2.11.6` 和固定哈希；IceGrid 三个程序的 `--version` 均为 `3.8.2`。

8. Quote、Trade、Derive 每个 `Version+No` 只有一个 READY Owner；Standby 不启动副作用，旧 fencing 写入被拒绝。
9. 两台 Nginx 配置检查通过并由 WinSW 运行，L4 VIP 能摘除任一故障入口；Gateway HTTP/WebSocket 端口正常。
10. `tools\MtGatewayServiceLoadTest\run_mt_gateway_service_pressure.bat` 完成 HTTP/WebSocket 压测，并按第一阶段门槛执行 10 万连接 N+1。
11. 主程序、HTTP、Web、CloudNetDataApi 和 `PushLog` 日志按服务/实例/类别隔离，没有互相混写。
12. 连续三轮强制结束六类 EXE，IceGrid 在 30 秒内重新拉起；状态型 Owner 在 20 秒内接管且无双主、重复交易或 SourceEpoch 回退。
13. 停止一个 NATS 节点业务继续；停止两个节点后状态型服务 10 秒内 fail closed，恢复 quorum 后只以 Standby 重新竞争。
14. `1172-1175` 的未 ACK 重投、DLQ、积压恢复和 Trade outbox 自动排空通过；同时记录节点本地 outbox 的整机丢失限制。
15. 完成 Registry Master、Nginx、Gateway/Event/Query 任一实例故障，10 万 WebSocket N+1 和 72 小时稳定性验收后，才允许申请生产平替。
