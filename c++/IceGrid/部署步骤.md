# IceGrid 3.8.2 部署步骤

## 1. 部署目标

本文档用于部署新版 IceGrid 注册中心，配合 `CloudNetDataApi` 和新版 `IceRPCPush.xml` 完成 MT 微服务插件的服务发现、连接重连、推送注册续约和动态接入。

新版部署包可以放在任意本地目录，本文统一使用以下占位路径：

```text
<IceGrid部署根目录>
```

例如，本项目内置副本的部署根目录是 `F:\gwz\trank\mt5-terminal-v3\tools\IceGrid`。安装脚本会按实际目录生成服务使用的绝对路径配置；已安装服务对应的目录不可直接移动，必须先卸载再移动并重新安装。

新版使用 Ice 3.8.2，不复用旧版 Ice 3.5.1 的二进制、配置数据库和运行目录。旧版部署包只作为流程参考。

## 2. 环境准备

1. 确认实际 IceGrid 部署根目录存在：

   ```text
   <IceGrid部署根目录>
   ```

2. 确认 `bin` 目录下使用的是 Ice 3.8.2 工具，以下命令在 cmd 中执行：

   ```bat
   cd /d <IceGrid部署根目录>
   bin\icegridregistry.exe --version
   bin\icegridadmin.exe --version
   ```

   期望输出版本为：

   ```text
   3.8.2
   ```

3. 确认本机 `18000` 端口未被占用。该端口是新版注册中心 Locator 入口。

4. 如果从旧环境迁移，不能复制旧版 `db/master`、旧版 `ice35.dll`、旧版 `icegrid35.dll` 或旧版 `icegridadmin.exe` 到新版目录。

## 3. 目录说明

新版 IceGrid 目录结构如下：

```text
IceGrid
├─ bin                 Ice 3.8.2 运行工具、服务安装器和依赖 DLL
├─ config              Registry、Node、Admin 配置和运行时服务配置
├─ app                 CloudNetDataApi 的 IceGrid 应用模板
├─ db                  新版 Registry 和 Node 运行数据库
├─ log                 Registry、Node 标准输出和错误日志
├─ doc                 说明文档
└─ tool                所有人工操作批处理
   ├─ install_icegrid_wtgrid.bat    安装并启动 Registry、Node 服务
   ├─ uninstall_icegrid_wtgrid.bat  停止并卸载 Registry、Node 服务
   ├─ start_registry.bat  启动已安装的 Registry 服务
   ├─ start_node.bat      启动已安装的 Node 服务
   ├─ admin.bat           进入 icegridadmin 控制台
   └─ deploy_app.bat      导入或更新 IceGrid 应用模板
```

## 4. 脚本总览

先根据场景选择脚本，不要把所有脚本依次运行一遍。

| 脚本 | 作用 | 何时运行 | 权限和结果 |
| --- | --- | --- | --- |
| `tool\install_icegrid_wtgrid.bat` | 检查 Ice 3.8.2、创建目录和服务配置，安装并启动本机 Registry 与 `CloudNetNode1`。 | 单机首次安装；服务卸载后重新安装。 | 必须管理员权限；成功后两个 Windows 服务在后台自动运行。 |
| `tool\start_registry.bat` | 启动已安装的 `icegridregistry.MtIceGrid` 并检查管理接口。 | Registry 已安装但处于停止状态；同节点重新部署的恢复阶段。 | 服务已经运行时只做健康检查；成功后立即退出。 |
| `tool\start_node.bat` | 启动已安装的 `icegridnode.MtIceGrid.CloudNetNode1`，并确认 Node1 已注册。 | Node1 已安装但处于停止状态；同节点重新部署的恢复阶段。 | 固定用于默认 Node1，不用于客户新增的 Node2。 |
| `tool\deploy_app.bat` | 查询 `application list`，自动选择 `application add` 或 `application update`。 | Registry、Node 就绪后首次部署或更新 `app\MtApplication.xml`。 | 不要求管理员权限；Registry 不可连接时不执行 add/update。 |
| `tool\admin.bat` | 打开交互式 `icegridadmin` 控制台。 | 查看 Node、应用、Adapter 和 Server 状态，或执行人工管理命令。 | 不要求管理员权限；退出控制台不会停止服务。 |
| `tool\uninstall_icegrid_wtgrid.bat` | 按 Node→Registry 顺序停止并卸载默认 Windows 服务。 | 移动部署目录、更改实例名/节点名/服务配置，或彻底移除服务。 | 必须管理员权限；保留 `db` 和 `log`。 |

所有脚本失败时返回非零错误码并显示日志位置。人工双击时保留默认暂停；自动化调用可以追加 `--nopause`，并必须检查 `%ERRORLEVEL%`。

### 4.1 普通运维最少需要记住的脚本

- 首次安装：`tool\install_icegrid_wtgrid.bat` → `tool\deploy_app.bat` → `tool\admin.bat`。
- Windows 正常重启：服务为自动启动，通常不需要人工运行脚本；只需用 `tool\admin.bat` 验证。
- 服务被人工停止：`tool\start_registry.bat` → `tool\start_node.bat`。
- 只更新应用 XML：`tool\deploy_app.bat`，不清 Node 数据，也不重装 Windows 服务。
- 同一 Node 重新部署：先停业务和服务、清 `db\node1` 内容，再执行 `tool\start_registry.bat` → `tool\start_node.bat` → `tool\deploy_app.bat` → `tool\admin.bat`。
- 移动目录或修改实例名、节点名：`tool\uninstall_icegrid_wtgrid.bat` → 修改配置 → `tool\install_icegrid_wtgrid.bat`。

### 4.2 客户可定制项和禁止直接修改项

| 文件 | 可以按客户环境修改 | 修改约束 |
| --- | --- | --- |
| `config\registry.cfg` | `MtIceGrid` 实例名、Registry 三组监听地址和端口、权限校验、Trace 级别。 | 多机部署不能继续使用 `127.0.0.1`；实例名变化后必须同步所有 Locator，并卸载后重装服务。 |
| `config\node.cfg` | Registry 地址、`IceGrid.Node.Name`、Node 监听地址、Trace 级别。 | 每个 Node 名和数据目录必须唯一；远程 Node 不得指向自身的 `127.0.0.1`。 |
| `config\admin.cfg` | Registry 地址、管理员账号和密码。 | Locator 的实例名、主机和端口必须与 Registry 一致。 |
| `app\MtApplication.xml` | 节点列表、`server-instance`、exe 绝对路径、激活方式和负载均衡策略。 | `application name="CloudNetDataApiGrid"` 已被部署脚本使用，修改时必须同步脚本；Server ID、Adapter ID 必须唯一。 |
| `CloudNetDataApi\conf\IceRPCPush.xml` | Locator、各服务监听 IP/端口、客户端回调地址、动态 Adapter ID 和副本组 ID。 | 同机多实例端口必须不同；跨机部署不能发布 `localhost`；副本组 ID 必须与 `MtApplication.xml` 完全一致。 |
| 批处理顶部变量 | 服务名、节点名、配置文件路径、显示名。 | 默认脚本彼此按 `MtIceGrid`/`CloudNetNode1` 固定配套；修改一个脚本后必须同步安装、启动、卸载和健康检查逻辑。 |

`config\service\registry.service.cfg` 和 `config\service\node.service.cfg` 是安装脚本生成的绝对路径配置，不作为客户配置入口，不要手工修改。要调整路径或基础配置，先修改 `config` 下的源配置，再卸载并重新安装服务。

## 5. 配置核对

部署前必须确认 IceGrid 配置和 `CloudNetDataApi\IceRPCPush.xml` 使用同一个 Locator。

### 5.1 registry.cfg

关键配置应保持如下：

```ini
IceGrid.InstanceName=MtIceGrid
Ice.Default.Locator=MtIceGrid/Locator:default -h 127.0.0.1 -p 18000
IceGrid.Registry.Client.Endpoints=default -h 127.0.0.1 -p 18000 -t 10000
IceGrid.Registry.LMDB.Path=db/registry
IceGrid.Registry.DynamicRegistration=1
```

说明：

- `IceGrid.InstanceName` 必须与 Locator 前缀 `MtIceGrid` 一致。
- `IceGrid.Registry.Client.Endpoints` 是插件、节点和管理工具访问注册中心的入口。
- `IceGrid.Registry.DynamicRegistration=1` 用于支持插件自行启动后动态注册到 Locator。
- 当前本地联调使用空权限校验，方便开发阶段调试。
- `tool\install_icegrid_wtgrid.bat` 会生成 `config\service\registry.service.cfg`，用当前部署根目录的绝对路径覆盖 LMDB 和日志目录；不要手工维护该文件。

### 5.2 node.cfg

关键配置应保持如下：

```ini
Ice.Default.Locator=MtIceGrid/Locator:default -h 127.0.0.1 -p 18000
IceGrid.Node.Name=CloudNetNode1
IceGrid.Node.Data=db/node1
```

说明：

- `IceGrid.Node.Name` 是当前节点名称，管理控制台中会显示为 `CloudNetNode1`。
- 当前 v1 插件进程默认由上层服务自行启动，Node 主要用于注册到 Registry 和后续托管能力预留。
- `tool\install_icegrid_wtgrid.bat` 会生成 `config\service\node.service.cfg`，用当前部署根目录的绝对路径覆盖 Node 数据和日志目录。

### 5.3 admin.cfg

关键配置应保持如下：

```ini
Ice.Default.Locator=MtIceGrid/Locator:default -h 127.0.0.1 -p 18000
IceGridAdmin.Username=admin
IceGridAdmin.Password=mtadmin
```

说明：

- `tool\admin.bat` 会读取该文件进入 IceGrid 管理控制台。
- 该 Locator 必须与 `registry.cfg` 完全一致。

### 5.4 CloudNetDataApi 的 IceRPCPush.xml

`CloudNetDataApi\IceRPCPush.xml` 中的 Locator 必须保持一致：

```xml
<Property name="Ice.Default.Locator" value="MtIceGrid/Locator:default -h 127.0.0.1 -p 18000" />
```

默认 6 插件的服务名和端口如下：

| 插件 | RPC 服务名 | 默认端口 | 职责 |
| --- | --- | ---: | --- |
| `Gateway` | `GatewayRPC` | 30001 | HTTP 入口、接口分发和 WebSocket 推送入口，不初始化 MT。 |
| `MtQuoteService` | `MtQuoteServiceRPC` | 30002 | 行情连接服务，接收 tick 并发布到统一事件中心。 |
| `MtTradeService` | `MtTradeServiceRPC` | 30003 | 合并交易事件、下单交易和配置事件能力。 |
| `MtQueryService` | `MtQueryServiceRPC` | 30004 | 合并普通查询、历史订单、成交、K线和 bars 查询。 |
| `IceEventService` | `IceEventServiceRPC` | 30005 | 统一事件中心，内部区分行情 best-effort 和可靠事件预留通道。 |
| `DeriveService` | `DeriveServiceRPC` | 30006 | 合并收益计算和 K线生成。 |

## 6. 6 插件整体部署拓扑

核心链路如下：

```text
HTTP 查询/下单：Client -> Gateway -> MtQueryService / MtTradeService
WebSocket 推送：Client <- Gateway <- IceEventService
行情事件：MtQuoteService -> IceEventService -> Gateway / DeriveService
交易和配置事件：MtTradeService -> IceEventService -> Gateway / DeriveService
派生计算：DeriveService -> IceEventService / MtQueryService
```

`CloudNetDataApi` 通过 `owner` 属性让同一份 XML 可以服务多个插件。`owner="Gateway"` 表示该连接或订阅只在 `LoadConfig(..., "Gateway")` 时生效；不写 `owner` 时兼容旧配置，对所有插件生效。

默认连接和订阅关系：

| 当前插件 | 自动连接 | 订阅 |
| --- | --- | --- |
| `Gateway` | `MtQueryService`、`MtTradeService`、`MtQuoteService`、`IceEventService` | 行情、订单、成交、持仓和收益事件。 |
| `MtQuoteService` | `IceEventService` | 默认不订阅，负责发布 tick。 |
| `MtTradeService` | `IceEventService` | 默认不订阅，负责发布交易、账户和配置事件。 |
| `MtQueryService` | 无 | 默认只提供查询服务。 |
| `IceEventService` | 无 | 默认只提供事件注册、续约和发布转发入口。 |
| `DeriveService` | `IceEventService`、`MtQueryService` | tick、持仓和保证金相关事件。 |

## 7. 从 12 插件到 6 插件的合并关系

| 原服务 | 合并后服务 | 说明 |
| --- | --- | --- |
| `HttpGateway`、`WsGateway` | `Gateway` | 入口统一，HTTP 分发和 WebSocket 推送共享网络连接管理。 |
| `MtQuoteService` | `MtQuoteService` | 行情连接独立保留，避免 tick 接收被其他业务阻塞。 |
| `MtTradeEventService`、`MtTradeCommandService`、`MtConfigService` | `MtTradeService` | 交易事件、交易指令和配置事件先放在同一交易域服务。 |
| `MtQueryService`、`MtHistoryService` | `MtQueryService` | 普通查询和历史查询先共享查询服务，后续按压力再拆。 |
| `IceMarketEventService`、`IceReliableEventService` | `IceEventService` | 第一版统一事件中心，内部按 topic 区分行情和可靠事件。 |
| `ProfitService`、`KlineService` | `DeriveService` | 派生计算统一承载收益和 K线生成。 |

## 8. 分场景操作

所有操作使用 cmd 或 `.bat`，不依赖 PowerShell。首次安装、卸载和 `sc start/stop` 必须使用管理员权限。

### 8.1 单机首次安装

本场景适用于一台 Windows 机器同时运行 Registry 和默认 `CloudNetNode1`。

1. 检查 `config\registry.cfg`、`config\node.cfg`、`config\admin.cfg` 和业务 `IceRPCPush.xml` 均指向同一个 Locator。
2. 以管理员身份运行 `tool\install_icegrid_wtgrid.bat`。
3. 安装成功后运行 `tool\deploy_app.bat`。
4. 运行 `tool\admin.bat`，执行 `node list`、`application list` 和 `adapter list`。

注意：

- 不要先单独运行 `tool\start_registry.bat` 或 `tool\start_node.bat`，它们只能启动已经安装的服务。
- 首次 Registry 没有应用数据，`tool\deploy_app.bat` 会自动执行 `application add`。
- 端口、实例名、节点名采用默认值时，不需要修改任何批处理。

### 8.2 日常启动和状态检查

两个服务默认配置为 Windows 自动启动。机器重启后先检查服务状态，再运行 `tool\admin.bat` 验证；只有服务确实处于停止状态时，才按以下顺序执行：

```bat
tool\start_registry.bat
tool\start_node.bat
tool\admin.bat
```

注意：Node 依赖 Registry，不能颠倒启动顺序。`tool\admin.bat` 只是管理客户端，不负责启动任何服务。

### 8.3 只更新应用描述

只修改 `app\MtApplication.xml` 中的 exe 路径、Server 实例或副本组时，Registry 和 Node 都保持运行，直接执行：

```bat
tool\deploy_app.bat
tool\admin.bat
```

这种更新不需要清空 `db\node1`，也不需要卸载 Windows 服务。部署前应先停止将被替换的业务进程，避免旧进程继续占用 exe 或端口。

### 8.4 卸载服务或迁移目录

以管理员身份运行：

```bat
tool\uninstall_icegrid_wtgrid.bat
```

脚本先卸载 Node，再卸载 Registry。卸载不会删除 `db`、`log` 和其中的数据；需要清理运行数据时必须人工确认后处理。

### 8.5 同一节点重新部署

Ice 3.5.1 在同一节点反复部署时，Node 本地数据库残留经常导致 Node 无法重新启动。Ice 3.8.2 的 `IceGrid.Node.Data` 仍保存 Node 本地状态和托管服务器配置，因此遇到同一节点重新部署时，继续采用“停止后清理 Node 数据、再按顺序启动”的方式。

Registry 和 Node 的数据职责不同：

| 目录 | 内容 | 常规重新部署 |
| --- | --- | --- |
| `db\registry` | Registry 的 LMDB 数据，包含应用定义、已知对象和部署信息。 | 必须保留。只有全新初始化 Registry 时才允许备份后清空。 |
| `db\node1` | `CloudNetNode1` 的本地状态和托管服务器配置。 | 停止 Node 后备份并清空内容，让 Node 重新建立状态。 |

重新部署必须严格执行以下顺序：

1. 停止 `Gateway`、`DeriveService`、MT 服务和 `IceEventService`。如果有 IceGrid 托管的服务器，也要先确认这些服务器已经停止。
2. 以管理员身份打开“服务”管理器，先停止 `icegridnode.MtIceGrid.CloudNetNode1`，确认状态已经变为“已停止”。
3. 再停止 `icegridregistry.MtIceGrid`，确认状态已经变为“已停止”。

   也可以在管理员 cmd 中执行：

   ```bat
   sc stop icegridnode.MtIceGrid.CloudNetNode1
   sc query icegridnode.MtIceGrid.CloudNetNode1
   sc stop icegridregistry.MtIceGrid
   sc query icegridregistry.MtIceGrid
   ```

   只有两个服务都完全停止后，才能处理数据库和覆盖程序文件。禁止在 Node 运行期间清理 `db\node1`。

4. 备份 `db\node1`，然后清空该目录中的文件和子目录。

   - 保留 `db\node1` 目录本身，不要删除后重建，避免丢失 LocalService 权限。
   - 不要清理 `db\registry`。
   - 不要把 Ice 3.5.1 的 Node 或 Registry 数据复制到 3.8.2。

5. 覆盖新版 `bin`、`config`、`app\MtApplication.xml` 和批处理脚本；保留 `db\registry`、`log` 和服务安装信息。
6. 先运行 Registry 启动脚本并等待健康检查通过：

   ```bat
   tool\start_registry.bat
   ```

7. 再运行 Node 启动脚本，确认 `CloudNetNode1` 重新注册：

   ```bat
   tool\start_node.bat
   ```

8. 部署应用描述：

   ```bat
   tool\deploy_app.bat
   ```

   `tool\deploy_app.bat` 会先执行 `application list`：

   - 没有 `CloudNetDataApiGrid` 时执行 `application add app\MtApplication.xml`。
   - 已存在 `CloudNetDataApiGrid` 时执行 `application update app\MtApplication.xml`。
   - Registry 无法连接时直接报错，不会误执行 `application add`。

9. 运行 `tool\admin.bat`，在管理控制台检查：

   ```text
   node list
   application list
   adapter list
   ```

正常结果是 `node list` 能看到 `CloudNetNode1`，`application list` 能看到 `CloudNetDataApiGrid`。

如果部署目录、`MtIceGrid` 实例名、`CloudNetNode1` 节点名或 Windows 服务配置发生变化，不能只停止后重启；应从原目录运行 `tool\uninstall_icegrid_wtgrid.bat`，再到新目录运行 `tool\install_icegrid_wtgrid.bat`。

### 8.6 远程 Node 接入同一个 Registry

示例网络：

| 机器 | 地址 | 角色 |
| --- | --- | --- |
| Registry 主机 | `10.20.0.10` | `MtIceGrid` Registry，可同时运行 `CloudNetNode1`。 |
| 业务主机 A | `10.20.0.21` | `CloudNetNode1` 或已有本地节点。 |
| 业务主机 B | `10.20.0.22` | 新增 `CloudNetNode2`。 |

先把 Registry 从“仅本机”改成局域网可访问。以下三个 Adapter 都要发布远程机器可达的地址，不能只改 Locator 端口：

```ini
IceGrid.Registry.Client.Endpoints=tcp -h 10.20.0.10 -p 18000 -t 10000
IceGrid.Registry.Server.Endpoints=tcp -h 10.20.0.10 -p 18001 -t 10000
IceGrid.Registry.Internal.Endpoints=tcp -h 10.20.0.10 -p 18002 -t 10000
Ice.Default.Locator=MtIceGrid/Locator:tcp -h 10.20.0.10 -p 18000
```

`Client` 供客户端、服务端、Node 和管理工具取得 Locator；`Server` 供业务 Server 注册；`Internal` 供远程 Node 与 Registry 通信。Registry 主机防火墙必须允许业务网段访问 TCP `18000`、`18001`、`18002`。修改 Registry 服务配置后，需要卸载并重新安装默认服务，不能只改 `registry.cfg` 后重启。

在业务主机 B 准备独立 `node2.service.cfg`：

```ini
Ice.Default.Locator=MtIceGrid/Locator:tcp -h 10.20.0.10 -p 18000
IceGrid.Node.Name=CloudNetNode2
IceGrid.Node.Endpoints=tcp -h 10.20.0.22 -p 18102
IceGrid.Node.Data=E:/MtIceTrading/IceGrid/db/node2
IceGrid.Node.Output=E:/MtIceTrading/IceGrid/log
Ice.StdOut=E:/MtIceTrading/IceGrid/log/node2_stdout.txt
Ice.StdErr=E:/MtIceTrading/IceGrid/log/node2_stderr.txt
Ice.ProgramName=CloudNetNode2
```

在业务主机 B 创建 `db\node2`、`log`，为 LocalService 授予修改权限，然后只安装 Node：

```bat
icacls "E:\MtIceTrading\IceGrid\db\node2" /grant "*S-1-5-19:(OI)(CI)M" /T /C
icacls "E:\MtIceTrading\IceGrid\log" /grant "*S-1-5-19:(OI)(CI)M" /T /C
bin\iceserviceinstall.exe --nopause --AutoStart 1 --DependOnRegistry 0 --DisplayName "MtIceGrid CloudNetNode2" icegridnode "config\service\node2.service.cfg"
sc start icegridnode.MtIceGrid.CloudNetNode2
```

远程 Node 必须使用 `--DependOnRegistry 0`。Windows 服务依赖只能依赖同一台机器的服务，不能让 Node2 依赖 Registry 主机上的 Windows 服务。默认 `tool\install_icegrid_wtgrid.bat` 会同时安装本机 Registry 和 Node1，因此不能直接在 Node2 主机运行；默认 `tool\start_node.bat` 也固定检查 Node1，Node2 使用上面的 `sc start`，并在 Registry 主机通过 `tool\admin.bat` 检查：

```text
node list
node show CloudNetNode2
```

远程 Node 接入成功只代表 Node 已加入 IceGrid，还不代表业务流量已经负载到该机器。必须继续在 `MtApplication.xml` 增加该 Node 的 `server-instance`，或者让业务进程以唯一 Adapter ID 动态加入同一副本组。

注意：

- `CloudNetNode1`、`CloudNetNode2` 名称必须唯一，`db\node1`、`db\node2` 也必须分开。
- Node2 主机应允许 Registry 主机访问 TCP `18102`。
- 业务 Adapter 发布的 IP 必须是其他机器可达的 `10.20.0.22`，不能发布 `127.0.0.1` 或 `localhost`。
- Registry、所有 Node、管理端和业务进程的实例名前缀必须都是 `MtIceGrid`。
- 远程 Node 卸载命令为 `bin\iceserviceinstall.exe --nopause --uninstall icegridnode "config\service\node2.service.cfg"`；保留 Node 数据目录。

## 9. 多节点、多实例与负载均衡

### 9.1 负载均衡生效的四个条件

当前 `MtApplication.xml` 已为 6 个 RPC 服务定义 `round-robin` 副本组。以行情服务为例：

```xml
<replica-group id="ReplicatedMtQuoteServiceRPC">
    <load-balancing type="round-robin" />
    <object identity="MtQuoteServiceRPC" type="::JSONBINRPC::IJsonBinRPC" />
</replica-group>
```

真正产生负载均衡还必须同时满足：

1. 至少两个正在运行的 `MtQuoteServiceRPC` Adapter 加入 `ReplicatedMtQuoteServiceRPC`。
2. 每个实例的 Adapter ID 唯一，但 `ReplicaGroupId` 相同。
3. 客户端使用 Locator 间接代理 `MtQuoteServiceRPC`，不能写死某台机器的 `IP:port`。
4. Registry、Node 和业务端点发布的是互相可达的真实 IP，防火墙允许访问。

只增加 Node、只启动第二个 exe，或者只写 `<load-balancing>` 都不会自动形成负载均衡。

`round-robin` 主要在代理解析、建立连接和重连时选择副本。当前 `CloudNetDataApi` 会长期复用连接，因此不能把它理解为“同一个 Gateway 的每一次调用严格轮流落到 A、B”。多个 Gateway、多个客户端或连接重建时会分散到不同副本；一个长连接通常会持续使用当前副本，故障后再解析并切换。

### 9.2 两台机器各部署一个 MtQuoteService.exe

如果 exe 已经支持读取 IceGrid 为托管 Server 生成的属性，推荐在同一个应用中声明两个 Server 实例：

```xml
<server-template id="MtQuoteServiceRPCServer">
    <parameter name="index" />
    <parameter name="exe" />
    <server id="MtQuoteServiceRPC-${index}" exe="${exe}" activation="always">
        <adapter name="MtQuoteServiceRPC"
                 endpoints="tcp -z"
                 replica-group="ReplicatedMtQuoteServiceRPC" />
        <property name="Identity" value="MtQuoteServiceRPC" />
    </server>
</server-template>

<node name="CloudNetNode1">
    <server-instance template="MtQuoteServiceRPCServer"
                     index="node1"
                     exe="E:/MtIceTrading/plugin/MtQuoteService.exe" />
</node>
<node name="CloudNetNode2">
    <server-instance template="MtQuoteServiceRPCServer"
                     index="node2"
                     exe="D:/MtIceTrading/plugin/MtQuoteService.exe" />
</node>
```

两个 Node 上的 exe 路径可以不同，Server ID 通过 `index` 保持唯一，Adapter 自动加入同一个副本组。更新 `MtApplication.xml` 后在 Registry 主机运行：

```bat
tool\deploy_app.bat
tool\admin.bat
```

然后在管理控制台检查两个 Server 和副本组 Adapter 均为 Active。

当前工程的 `MtApplication.xml` 仍明确标记为“后续切换到 IceGrid 托管进程”的模板。只有 `MtQuoteService.exe` 会读取 IceGrid 传入的 Server 配置时，才可以直接采用上面的托管方式；否则 exe 内部重新从自己的 `IceRPCPush.xml` 创建 Communicator，会忽略 IceGrid 生成的端口和 Adapter 属性。

在当前“业务进程自行启动”模式下，两台机器分别使用独立的 `IceRPCPush.xml`，通过动态 Adapter 加入副本组。机器 A 的行情服务配置示例：

```xml
<Property name="Ice.Default.Locator" value="MtIceGrid/Locator:tcp -h 10.20.0.10 -p 18000" />
<Property name="MtQuoteServiceRPC.Endpoints" value="tcp -z -h 10.20.0.21 -p 30002" />
<Property name="MtQuoteServiceRPC.AdapterId" value="MtQuoteServiceRPC.Node1.Instance1" />
<Property name="MtQuoteServiceRPC.ReplicaGroupId" value="ReplicatedMtQuoteServiceRPC" />
<Property name="MtQuoteServiceRPC" value="MtQuoteServiceRPC" />
```

机器 B 只改变真实 IP 和唯一 Adapter ID：

```xml
<Property name="Ice.Default.Locator" value="MtIceGrid/Locator:tcp -h 10.20.0.10 -p 18000" />
<Property name="MtQuoteServiceRPC.Endpoints" value="tcp -z -h 10.20.0.22 -p 30002" />
<Property name="MtQuoteServiceRPC.AdapterId" value="MtQuoteServiceRPC.Node2.Instance1" />
<Property name="MtQuoteServiceRPC.ReplicaGroupId" value="ReplicatedMtQuoteServiceRPC" />
<Property name="MtQuoteServiceRPC" value="MtQuoteServiceRPC" />
```

`MtApplication.xml` 中必须先存在 `ReplicatedMtQuoteServiceRPC` 和对象 `MtQuoteServiceRPC`，Registry 必须启用 `IceGrid.Registry.DynamicRegistration=1`。分别启动两个 `MtQuoteService.exe` 后，通过 `tool\admin.bat` 的 `adapter list`/`adapter show` 确认两个唯一 Adapter 都已注册。

### 9.3 同一台机器部署两个 MtQuoteService.exe

同机双实例只需要一个 IceGrid Node，但两个进程必须使用两份独立配置和不同端口：

| 配置 | 实例 1 | 实例 2 |
| --- | --- | --- |
| 进程目录 | `E:\MtQuote\instance1` | `E:\MtQuote\instance2` |
| Adapter ID | `MtQuoteServiceRPC.Node1.Instance1` | `MtQuoteServiceRPC.Node1.Instance2` |
| Replica Group ID | `ReplicatedMtQuoteServiceRPC` | `ReplicatedMtQuoteServiceRPC` |
| RPC 端口 | `30002` | `31002` |
| 日志目录 | 独立 | 独立 |

实例 2 的关键配置：

```xml
<Property name="MtQuoteServiceRPC.Endpoints" value="tcp -z -h 10.20.0.21 -p 31002" />
<Property name="MtQuoteServiceRPC.AdapterId" value="MtQuoteServiceRPC.Node1.Instance2" />
<Property name="MtQuoteServiceRPC.ReplicaGroupId" value="ReplicatedMtQuoteServiceRPC" />
```

如果改为 IceGrid 托管，则在同一个 `<node name="CloudNetNode1">` 内放两个 `server-instance`：

```xml
<node name="CloudNetNode1">
    <server-instance template="MtQuoteServiceRPCServer"
                     index="node1-1"
                     exe="E:/MtQuote/instance1/MtQuoteService.exe" />
    <server-instance template="MtQuoteServiceRPCServer"
                     index="node1-2"
                     exe="E:/MtQuote/instance2/MtQuoteService.exe" />
</node>
```

注意：

- 两个进程不能同时绑定 `30002`；回调、快速推送或业务管理端口如启用，也必须逐项错开。
- 两个实例不能共用可写日志、缓存、锁文件或 MT 会话目录。
- 两个实例连接同一个 MT 行情源时，可能产生重复 tick；负载均衡只解决 RPC 请求分配，不自动做行情去重。
- 对有会话、订阅、订单状态或本地缓存的服务，先确认状态共享和幂等策略，再加入轮询副本组。

### 9.4 多节点变更的正确发布顺序

1. 先部署并启动 Registry，确认三组远程端点和防火墙正常。
2. 逐台安装/启动 Node，确认 `node list` 能看到唯一节点名。
3. 把 exe 和每台机器专属配置放到目标路径。
4. 更新 `MtApplication.xml` 的 Node/Server 实例，或配置自行启动进程的唯一 Adapter ID。
5. 运行 `tool\deploy_app.bat`。
6. 启动业务实例并通过 `adapter list`、`adapter show` 检查每个副本。
7. 从至少两个客户端发起请求并停止其中一个实例，验证分流和故障切换。

不要为了新增 Node 清空 `db\registry`；不要把 Node1 的 `db` 复制给 Node2；不要让两台机器使用相同 `IceGrid.Node.Name` 或相同动态 Adapter ID。

## 10. 业务插件启动顺序

推荐启动顺序：

1. 启动 `IceEventService`，先提供事件注册和发布入口。
2. 启动 `MtQuoteService`、`MtTradeService`、`MtQueryService`。
3. 启动 `DeriveService`，向事件中心注册订阅。
4. 启动 `Gateway`，建立对内部服务的连接并注册前端推送需要的订阅。

每个插件内部建议使用以下流程：

```cpp
HCLOUD_NET_API hApi = Create();
LoadConfig(hApi, "IceRPCPush.xml", "Gateway");
StartNetwork(hApi, OnRequest, OnPush, pUserParam);
```

其中第三个参数按插件实际身份传入：

```text
Gateway
MtQuoteService
MtTradeService
MtQueryService
IceEventService
DeriveService
```

## 11. HTTP 入口分发示例

`Gateway` 收到 HTTP 请求后，由自身业务路由决定调用哪个远端服务：

```text
查询请求：Gateway -> CallSync("MtQueryService", ...)
历史请求：Gateway -> CallSync("MtQueryService", ...)
下单请求：Gateway -> PutSync("MtTradeService", ...)
配置请求：Gateway -> CallAsync("MtTradeService", ...)
行情管理：Gateway -> CallSync("MtQuoteService", ...)
```

`CallSync`、`CallAsync`、`PutSync`、`PutAsync` 中的连接名使用 XML 中 `<Service id="...">` 的 id，例如 `MtQueryService`、`MtTradeService`。

## 12. 行情推送验证

验证链路：

1. 启动 `IceEventService`。
2. 启动 `Gateway`、`DeriveService`，它们会向 `IceEventService` 执行 `RegisterPush`。
3. 启动 `MtQuoteService`。
4. `MtQuoteService` 收到行情后调用 `Publish` 或业务封装发布 tick 到 `IceEventService`。
5. `IceEventService` 再把 tick 推送给已注册的 `Gateway` 和 `DeriveService`。

预期结果：

- `Gateway` 能收到后续行情并转发前端 WebSocket 客户端。
- `DeriveService` 能收到 tick，为收益计算和 K线生成准备输入。
- 已启动后的新插件只接收后续推送，历史行情仍需要通过 RPC 拉取或业务快照补偿。

## 13. 动态接入和重启恢复

如果新增或重启某个插件：

- 只要该插件已在 `IceRPCPush.xml` 中预置，其他插件后台维护线程会通过 Locator 自动重连。
- 如果配置是运行后新增的，需要先更新 `IceRPCPush.xml`，再由相关插件调用 `ReloadConfig`。
- 推送订阅会按 `renewIntervalSec` 定时续约，默认 240 秒。

如果 `MtTradeService` 或 `MtQueryService` 重启：

- `Gateway` 的后台线程会持续尝试重连。
- 重启期间相关 HTTP 请求应由 `Gateway` 返回明确错误或降级响应。
- 重连成功后，新的请求会恢复转调。

## 14. 可靠事件中心说明

`IceEventService` 第一版统一承载行情事件通道和可靠事件预留通道。

当前网络库已经具备推送注册和发布推送基础能力，但可靠事件的以下能力仍由后续插件源码实现：

- 发布前落库。
- 消费者 ACK。
- 断线 Replay。
- 消费者进度管理。
- 保留期清理。

因此当前部署文档只预留服务名、端口、连接关系和订阅关系，不把可靠事件中心描述成已经完整实现。

## 15. 后续拆分条件

- `Gateway`：当 WebSocket 推送压力影响 HTTP 接口响应时，再拆回 HTTP 入口和 WebSocket 入口。
- `MtTradeService`：当下单链路需要独立灰度、串行化或故障隔离时，再拆出交易指令服务。
- `MtQueryService`：当历史查询明显拖慢普通查询时，再拆出历史查询服务。
- `IceEventService`：当可靠事件 ACK、Replay、落库实现后，再拆为行情事件中心和可靠事件中心。
- `DeriveService`：当收益计算或 K线生成 CPU、内存压力明显时，再拆为独立派生服务。

## 16. 停止顺序

推荐停止顺序：

1. 停止入口服务：`Gateway`。
2. 停止派生服务：`DeriveService`。
3. 停止 MT 服务：`MtQuoteService`、`MtTradeService`、`MtQueryService`。
4. 停止事件中心：`IceEventService`。
5. 停止 Node。
6. 停止 Registry。

## 17. 故障排查与解决方法

### 17.1 固定排查顺序

遇到失败时按证据逐层排查，不要一开始就删除数据库：

1. 保留失败脚本窗口，记录 `[ERROR]`、错误码、执行到的命令和日志路径。
2. 用 `sc query` 确认 Windows 服务状态，用 `sc qc` 确认服务路径、启动账户和依赖。
3. 先看 `log\registry_stderr.txt`，再看对应 `node*_stderr.txt` 和托管业务进程输出。
4. Registry 可连接后，用 `tool\admin.bat` 依次检查 `node list`、`application list`、`server list`、`adapter list`。
5. 用 `netstat -ano` 核对监听端口，用 `ping` 或 `Test-NetConnection` 从对端验证网络和防火墙。
6. 对照实例名、Node 名、Adapter ID、Replica Group ID、真实 IP 和端口，确认所有配置联动一致。
7. 只有日志明确指向 Node 本地状态损坏，或按同节点重新部署流程操作时，才备份并清空对应 `db\node*` 内容；常规故障不得清空 `db\registry`。

常用只读命令：

```bat
sc query icegridregistry.MtIceGrid
sc qc icegridregistry.MtIceGrid
sc query icegridnode.MtIceGrid.CloudNetNode1
sc qc icegridnode.MtIceGrid.CloudNetNode1
netstat -ano | findstr ":18000"
netstat -ano | findstr ":30002"
bin\icegridregistry.exe --version
bin\icegridnode.exe --version
bin\icegridadmin.exe --version
```

### 17.2 安装和 Windows 服务失败

| 现象 | 排查 | 解决 |
| --- | --- | --- |
| 总脚本提示权限不足 | `fltmc` 返回拒绝访问，或服务安装器报 access denied。 | 右键 cmd/脚本“以管理员身份运行”。 |
| 提示缺少 exe/DLL 或版本错误 | 运行三个 `--version`，检查 `bin` 是否混入 Ice 3.5.1。 | 恢复完整 Ice 3.8.2 `bin`，不要复制旧版 DLL。 |
| 服务已存在但指向其他目录 | `sc qc <服务名>` 和注册表 `ImagePath` 显示旧路径。 | 回到旧目录运行卸载脚本；确认服务消失后在新目录重新安装。 |
| Registry 服务启动后立即停止，错误 1067 | 查看 `registry_stderr.txt`，检查 LMDB 路径、ACL、端口和配置语法。 | 修正权限/端口/配置；若服务配置路径变化，卸载后重新安装。 |
| Node 服务启动后立即停止 | 查看 `node_stderr.txt`，检查 Locator、Node 数据 ACL 和 Node 名冲突。 | 修正配置；同节点反复部署且日志指向本地状态时，按 8.5 节备份清理 Node 数据。 |
| 远程 Node 报服务依赖不存在或错误 1075 | `sc qc` 显示依赖远程 Registry 的服务名，但远程主机本地没有该服务。 | 卸载该 Node，使用 `--DependOnRegistry 0` 重新安装。 |
| LocalService 无法写 db/log | stderr 出现 access denied；`icacls` 未包含 SID `S-1-5-19` 的修改权限。 | 对对应 `db\node*`、`db\registry` 和 `log` 重新授予 `(OI)(CI)M`。 |

### 17.3 Registry、Node 和部署失败

| 现象 | 排查 | 解决 |
| --- | --- | --- |
| `tool\admin.bat` 或 `application list` 连接失败 | 检查 Registry 是否 Running、`18000` 是否监听、admin.cfg Locator 是否一致。 | 先恢复 Registry；多机环境从管理机测试 `10.20.0.10:18000` 防火墙。 |
| Registry 本机正常，远程全部失败 | Registry 的 Client/Server/Internal 仍发布 `127.0.0.1`，或只开放 Client 端口。 | 三组端点都改为真实业务网 IP和固定端口，开放防火墙后重装 Registry 服务。 |
| Node 服务 Running，但 `node list` 看不到 | Node Locator 错误、Registry Internal 端点不可达、Node 名冲突。 | 修正 Node 的 Registry IP，开放 Internal 和 Node 端口，为每台机器使用唯一 Node 名。 |
| `tool\deploy_app.bat` 返回 list 失败 | 当前 Registry 不可连接；脚本不会继续 add/update。 | 先修复 Registry，再重新运行部署脚本。 |
| `application add` 提示应用已存在 | Registry 保留了原应用数据。 | 使用当前 `tool\deploy_app.bat` 自动选择 update，不要手工重复 add。 |
| `application update` 提示 XML/Node/Server 错误 | XML 语法错误、引用不存在 Node、Server ID 重复或 exe 参数不合法。 | 先确认 `node list`，再检查 XML 中 node 名、模板参数和唯一 ID，修正后重新 update。 |
| 清空 Registry 后 `application list` 为空 | `db\registry` 保存的应用定义已经丢失。 | 从备份恢复，或运行 `tool\deploy_app.bat` 重新执行 application add；常规重部署不应清空 Registry。 |

### 17.4 业务实例和负载均衡失败

| 现象 | 排查 | 解决 |
| --- | --- | --- |
| 第二个 MtQuoteService 启动报端口占用 | `netstat -ano | findstr ":30002"` 显示第一个实例已监听。 | 同机实例改用不同 RPC、回调、推送和管理端口，例如第二实例用 `31002`。 |
| `adapter list` 只有一个行情 Adapter | 第二实例没有启动，两个实例误用相同 Adapter ID，或没有配置 ReplicaGroupId。 | 为每个实例设置唯一 `MtQuoteServiceRPC.AdapterId`，共同使用 `ReplicatedMtQuoteServiceRPC`。 |
| Adapter 存在但无可用端点 | 业务进程未激活、发布了 `127.0.0.1`/错误网卡，或远程端口被防火墙拦截。 | 改成对端可达的业务网 IP，确认进程监听和防火墙，再重启实例。 |
| 客户端一直连固定 IP，未走副本组 | `IceRPCPush.xml` 中代理写成 `Identity:tcp -h ...`，绕过 Locator。 | 使用 `Ice.Default.Locator` 和间接代理 `MtQuoteServiceRPC`。 |
| 配了 round-robin，但单个 Gateway 长期只访问一个实例 | 当前客户端复用长连接；轮询发生在解析、建连或重连，不是每次调用。 | 用多个客户端验证分散效果，并做停机重连测试；若业务要求逐请求分流，应在 Gateway 增加专门调度策略。 |
| 停掉一个副本后请求仍失败 | 客户端未重新解析、另一个 Adapter 未 Active，或重连窗口尚未结束。 | 检查另一个 Adapter 端点，等待后台重连；核对 `reconnectIntervalMs` 和 Locator 日志。 |
| 双行情实例产生重复 tick | 两个实例都连接同一行情源并向事件中心发布相同数据。 | 按账户/市场分片，或在事件中心增加事件唯一键和去重；IceGrid 轮询本身不提供事件去重。 |
| 有状态服务负载后数据不一致 | 订阅、订单、会话或缓存保存在单机内存。 | 先实现共享状态、粘性路由或幂等，再扩为副本；不满足条件时保持单实例。 |
| 推送收不到 | 消费者未连接 `IceEventService`、订阅未启用、回调端点发布 localhost 或续约超时。 | 检查连接、订阅、回调真实 IP，以及 `renewIntervalSec` 是否小于服务端超时。 |

### 17.5 其他问题

| 现象 | 解决 |
| --- | --- |
| 中文日志乱码 | 从批处理进入 UTF-8 控制台；脚本已执行 `chcp 65001`，配置、XML 和文档统一保存为 UTF-8。 |
| 同一 Node 重新部署后仍启动失败 | 确认严格按 Node→Registry 停止，两个服务完全停止后才清 `db\node1` 内容，再按 Registry→Node 启动；不要删除目录本身。 |
| 误用 Ice 3.5.1 数据 | 不做数据库升级混用；使用全新的 3.8.2 Node 数据，Registry 应按正式迁移方案重新部署应用。 |
